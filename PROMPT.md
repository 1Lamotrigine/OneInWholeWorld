# PROMPT.md — Техническое задание и план разработки

> Проект: **Fantasy Life** (рабочее название). Версия документа: 0.1. Статус: проектирование MVP.
>
> Этот файл — основное техническое руководство для разработчика или AI coding agent. Концепция, игровой мир и контент описаны в [`IDEA.md`](./IDEA.md). При противоречии в игровых правилах приоритет имеет `IDEA.md`, в технических решениях — `PROMPT.md`.

## 1. Цель проекта

Создать браузерную, полностью клиентскую, local-first игру на Next.js, вдохновлённую принципом случайного рождения и симуляции жизни из «1 из 8 миллиардов», но в оригинальном фэнтезийном мире. Пользователь получает случайную расу, место рождения, семью, социальное положение и стартовые свойства, наблюдает течение жизни и принимает решения в ключевые моменты. Игра должна быть интересной без сервера, аккаунтов, облачного сохранения и генеративного AI.

**Ключевые ограничения:**
- Вся игровая логика выполняется в браузере. Не создавать API routes, server actions, серверные БД и обязательные внешние сервисы.
- Next.js используется как оболочка и UI; страницы игры могут быть client components. Статические страницы допустимо пререндерить.
- Персистентность — PGlite в IndexedDB. Инициализация базы только на клиенте; не импортировать браузерные модули в серверный код.
- Игра работает без сети после загрузки необходимых ресурсов (полный offline/PWA — отдельный этап).
- Игровая симуляция отделена от React, Zustand, PGlite и UI. Все правила проверяемы автоматическими тестами.
- Не копировать интерфейс, тексты, графику, названия игровых сущностей или контент сайта-референса.

## 3. Основные пользовательские сценарии

1. Открыть стартовую страницу, узнать принцип игры, нажать «Родиться».
2. Получить **случайно** сгенерированного персонажа с объяснением его происхождения и вероятностей.
3. Наблюдать жизнь: возраст, характеристики, место, статус, профессию, летопись.
4. Поставить время на паузу, продолжить или ускорить симуляцию.
5. Важное событие может потребовать решения; выбор влияет на дальнейшие состояния и вероятности.
6. Включить авторежим, чтобы решения выбирались по приоритетам персонажа.
7. Закрыть вкладку, вернуться и восстановить сохранение.
8. После смерти увидеть итог жизни и начать новую, не теряя прошлую летопись.
9. Экспортировать сохранение в файл и импортировать его на другом устройстве.

## 4. Архитектурные принципы

### 4.1 Разделение слоёв

```text
React UI (Next.js Client Components)
             ↕
Zustand (сессия, управление временем, UI)
             ↕
Application services (новая игра, шаг, выбор, save/load)
             ↕
Pure Game Engine (TypeScript, seedable RNG)
             ↕
Game content (versioned TS/JSON definitions)

Persistence adapter (PGlite/IndexedDB) ↔ Application services
```

- **Game Engine** — чистые функции: вход `GameState + Command + RandomState`, выход `GameState + DomainEvents + RandomState`. Никакого DOM, React, SQL, `Date.now()` и прямого `Math.random()`.
- **Content** — неизменяемые определения рас, регионов, статусов, профессий, событий, весов и условий.
- **Application** — оркестрация тиков, выборов, сохранения, миграций, экспорта.
- **Persistence** — изолированный интерфейс репозитория; движок не знает, что используется PGlite.
- **UI** — отображение состояния и отправка команд; не рассчитывает игровые вероятности.

### 4.2 Генерация случайностей

Использовать детерминированный PRNG с сохраняемым состоянием. `seed` нужен для воспроизводимости, но **одного seed недостаточно**: сохранять текущее состояние генератора или счётчик потреблённых случайных чисел. Не полагаться на `Math.random()` внутри движка. В тестах передавать контролируемый источник случайности.

Взвешенный выбор работает по сумме неотрицательных весов. Запрещены пустые наборы, отрицательные веса и ситуации, когда сумма равна нулю. Вероятности должны вычисляться с учётом условий (расы, региона, семьи, эпохи), а не только глобальной таблицы.

### 4.3 Время

- Симуляция **дискретная**, основной шаг — игровой год (при необходимости внутри года рассчитываются фазы).
- Визуальная скорость — настройка UI: пауза / 1× / 2× / 5×. Конкретные миллисекунды на год настраиваются отдельно от правил.
- На каждом шаге: старение → базовые потребности и характеристики → семейные/социальные изменения → изменения региона/мира → подходящие события → последствия → проверка смерти.
- Порядок расчёта фиксирован и документирован; повторная обработка одного события в рамках тика исключена.
- При событии с обязательным выбором симуляция ставится на паузу. В авторежиме выбирается допустимое действие по приоритетам и правилам.
- Не пытаться «догонять» прошедшие в реальности часы после закрытия браузера: игра возобновляется с сохранённого игрового времени.

### 4.4 Мир и NPC

**MVP:** симулировать подробно только персонажа игрока; остальной мир представлен агрегированными параметрами регионов (безопасность, благополучие, конфликт, магическая нестабильность), а близкие NPC — компактными записями по необходимости. Не симулировать миллионы жителей по отдельности. Полноценная динамика населения и династий — отдельный этап.

## 5. Модель данных (домен)

Рекомендуемые сущности:

```ts
type RaceId = 'human' | 'elf' | 'dwarf' | 'orc' | 'goblin';
type RegionId = string;
type ProfessionId = string;
type SocialStatusId = string;
type EventId = string;

type Stats = {
  health: number;       // 0..100
  happiness: number;    // 0..100
  intellect: number;    // 0..100
  strength: number;     // 0..100
  charisma: number;     // 0..100
  magic: number;        // 0..100; потенциал ≠ обученность
};

type Character = {
  id: string;
  name: string;
  raceId: RaceId;
  regionId: RegionId;
  age: number;
  alive: boolean;
  familyBackgroundId: string;
  socialStatusId: SocialStatusId;
  professionId: ProfessionId | null;
  stats: Stats;
  traits: string[];
  wealth: number;
  relationships: Relationship[];
};

type WorldState = {
  year: number;
  regions: Record<RegionId, RegionState>;
};

type PendingDecision = {
  eventInstanceId: string;
  eventId: EventId;
  optionIds: string[];
} | null;

type GameState = {
  schemaVersion: number;
  contentVersion: string;
  saveId: string;
  seed: string;
  rngState: number[];
  character: Character;
  world: WorldState;
  pendingDecision: PendingDecision;
  ended: boolean;
};
```

`Relationship` и `RegionState` определить отдельно. Числовые диапазоны и ограничения проверять в движке и тестах. Все ID — стабильные идентификаторы, не отображаемые названия. События в летописи — отдельные записи с игровым годом, типом, шаблоном и параметрами. Текст летописи должен оставаться понятным после обновления контента (хранить разрешённый текст или версионированные параметры шаблона).

## 6. Система событий

Определения событий — данные, а не `if`-цепочки в UI:

```ts
type EventDefinition = {
  id: string;
  category: 'family' | 'work' | 'health' | 'politics' | 'magic' | 'adventure';
  minAge?: number;
  maxAge?: number;
  weight: number;
  cooldownYears?: number;
  isEligible: (state: GameState) => boolean;
  options?: EventOption[];
  apply: (state: GameState, rng: RandomSource) => EventResult;
};
```

Если определения хранятся в JSON, вместо функций использовать декларативные условия и эффекты, обрабатываемые интерпретатором. **Не сериализовать функции в JSON и не исполнять строки через `eval`.**

Правила:
- Сначала фильтровать по возрасту, расе, региону, статусу, профессии, состоянию мира и cooldown.
- Затем выполнять взвешенный выбор среди допустимых событий.
- Событие имеет последствия, возможно отложенные, и запись в летописи.
- Опции должны иметь явные предусловия, стоимость, эффект и fallback для авторежима.
- Уникальные события и смерти не должны повторяться.
- В MVP избегать ситуаций без доступного действия; предусмотреть безопасный вариант по умолчанию.

## 7. Хранение в PGlite

PGlite запускается в браузере, хранение — `idb://fantasy-life`. Желательно изолировать экземпляр БД в Web Worker (или внедрить worker на этапе оптимизации). Не создавать новый экземпляр при каждом React-render. Контролировать доступ из нескольких вкладок: использовать поддерживаемый worker/multitab-механизм или блокировать параллельную запись в один save.

Начальная схема:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
  version INTEGER PRIMARY KEY,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS saves (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  schema_version INTEGER NOT NULL,
  content_version TEXT NOT NULL,
  seed TEXT NOT NULL,
  state JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS life_events (
  id TEXT PRIMARY KEY,
  save_id TEXT NOT NULL REFERENCES saves(id) ON DELETE CASCADE,
  game_year INTEGER NOT NULL,
  sequence INTEGER NOT NULL,
  event_type TEXT NOT NULL,
  description TEXT NOT NULL,
  data JSONB NOT NULL DEFAULT '{}'::jsonb,
  UNIQUE(save_id, sequence)
);

CREATE INDEX IF NOT EXISTS idx_life_events_save_sequence
  ON life_events(save_id, sequence);
```

Запись состояния и соответствующих записей летописи — **одной транзакцией**. Миграции схемы обязательны. Сохранение по завершении тика, после решения, при уходе на паузу и периодически; не выполнять SQL на каждом кадре анимации. Нельзя полагаться только на `beforeunload`.

**Экспорт/импорт:** JSON с `formatVersion`, `schemaVersion`, `contentVersion`, метаданными, состоянием и летописью. Проверять структуру, ограничения размера, ID, совместимость версий и целостность до записи. Не импортировать произвольный SQL. Поддержать удаление сохранений и понятное предупреждение об очистке данных браузера.

## 9. UI и UX

**Страницы:**
- `/` — атмосферная стартовая страница, объяснение случайного рождения, кнопка новой жизни, продолжение сохранения.
- `/game` — персонаж, возраст/год, регион, параметры, лента событий, выборы, скорость и пауза.
- `/archive` — завершённые и активные жизни, итоговые карточки, импорт/экспорт.

**Обязательные состояния:** первая загрузка PGlite, миграция, пустая база, сохранение, ошибка хранения, пауза, обязательный выбор, смерть, конец жизни. Интерфейс должен работать на мобильных экранах, иметь доступные кнопки, клавиатурную навигацию и настройки уменьшения анимации. Не использовать цвет как единственный индикатор статуса.

## 10. Производительность и надёжность

- Не делать полную запись состояния после каждого визуального кадра.
- Ограничить количество одновременно отрисованных элементов летописи (виртуализация при необходимости).
- Тяжёлые расчёты перенести в Worker после появления реальной нагрузки; не оптимизировать преждевременно.
- Проверять доступность IndexedDB, обрабатывать quota errors и приватный режим.
- Никаких запросов на сервер для игрового прогресса; внешние шрифты/изображения не должны быть обязательными для офлайн-игры.
- Проверять production build с выбранной стратегией статического хостинга. При полностью статическом размещении использовать `output: 'export'`, только если все маршруты и используемые возможности с ним совместимы.

## 11. Этапы разработки

### Этап 0 — Каркас
- Инициализировать Next.js, TypeScript strict, Tailwind, линтер, тесты.
- Создать страницы и базовые компоненты.
- Зафиксировать интерфейсы движка и правила из `IDEA.md`.

**Готово, когда:** проект запускается, собирается и проходит пустой набор smoke-тестов.

### Этап 1 — Генерация рождения
- Добавить 5 рас, 5–8 регионов, семьи, статусы, имена, стартовые характеристики.
- Реализовать seedable RNG и условные вероятности.
- Показать карточку рождения и шанс происхождения.

**Готово, когда:** один seed воспроизводит одно рождение; веса покрыты тестами.

### Этап 2 — Жизненный цикл
- Годовые тики, старение, характеристики, смерть, скорость/пауза.
- Минимум 30 событий без решений, летопись.

**Готово, когда:** персонаж может прожить жизнь от рождения до финального экрана.

### Этап 3 — Решения и авторежим
- Минимум 30 событий с выбором, эффекты и ограничения.
- Пауза на решениях, приоритеты авторежима.
- Базовые профессии и смена социального положения.

**Готово, когда:** разные решения из одного состояния приводят к разным проверяемым последствиям.

### Этап 4 — Локальные сохранения
- PGlite + IndexedDB, миграции, репозиторий.
- Автосохранение, загрузка, архив, удаление, импорт/экспорт.

**Готово, когда:** жизнь восстанавливается после перезагрузки и импортируется из файла.

### Этап 5 — Наполнение и полировка MVP
- Довести контент до 100–150 событий.
- Баланс вероятностей, экономика, региональные кризисы, магия, семейные события.
- Мобильная адаптация, доступность, оптимизация, E2E.

**Готово, когда:** возможны разные правдоподобные жизненные истории без тупиков и критических ошибок.

### После MVP
- Династии, наследники, развитые NPC, межрегиональные миграции.
- PWA/offline precaching, достижения, статистика прохождений.
- Расширение рас и континентов; моддинг через валидируемые пакеты контента.

## 12. Тесты и критерии приёмки

**Unit:** воспроизводимость RNG, сумма весов, невозможные комбинации происхождения, ограничения характеристик, порядок тика, условия событий, cooldown, эффекты выбора, смерть и завершение.

**Integration:** создание/загрузка PGlite, миграции, транзакционное сохранение, восстановление RNG, экспорт/импорт, удаление.

**E2E:** новая жизнь → несколько тиков → выбор → сохранение → reload → продолжение → смерть → архив.

**Баланс:** симулировать тысячи жизней автоматически; сравнивать распределения рас с заданными весами, находить недостижимые профессии, аномальную смертность и бесконечные циклы. Статистические проверки должны иметь допуски, а не требовать точных процентов в маленькой выборке.

## 13. Правила для AI coding agent

1. Перед изменением механик прочитать `IDEA.md` и этот файл.
2. Реализовывать поэтапно, не создавать весь проект одним гигантским коммитом.
3. Не добавлять backend, API, Prisma, облачную БД, аккаунты или AI без отдельного запроса.
4. Сохранять чистоту игрового движка; не переносить правила в React-компоненты.
5. Не подменять детерминированный RNG `Math.random()`.
6. Для нового события определять условия, вес, последствия, отображаемый текст и тест.
7. Любое изменение формата сохранения сопровождать версией и миграцией.
8. Не объявлять этап готовым без запуска соответствующих тестов и production build.
9. При неопределённости сначала предлагать минимальное решение и явно фиксировать допущения.
10. Использовать `IDEA.md` как источник игрового лора; не вводить новые расы или королевства молча.

## 14. Что сознательно не входит в MVP

Мультиплеер, серверная синхронизация, аккаунты, внутриигровые платежи, глобальные таблицы лидеров, генеративный AI, полноценная экономика каждого NPC, пошаговые сражения с картой, инвентарь с сотнями предметов, процедурная 3D-карта, полноценная симуляция миллионов жителей.
